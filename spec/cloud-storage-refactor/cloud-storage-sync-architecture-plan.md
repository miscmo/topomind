## 1. 文档目的

本文档用于回答 TopoMind 从“本地文件系统工作目录”演进到“账号登录 + 云端存储 + 多端同步”时的核心设计问题：

- TopoMind 当前的数据形态是否适合使用关系型数据库
- 卡片树、图关系、智能笔记、思维导图、流程图、附件分别应该如何存储
- 是否需要图数据库、文档数据库、对象存储、搜索引擎等额外组件
- 当前代码架构与本地路径模型对云化的主要阻碍是什么
- 什么样的技术栈组合最适合作为长期产品底座
- 如何以尽量低风险的方式，从当前本地版逐步迁移到云同步版

本文档的目标不是仅给出“用什么数据库”的单点答案，而是形成一套适合 TopoMind 现状与未来演进方向的完整底层方案。

## 2. 执行摘要

### 2.1 最终结论

TopoMind 后续如果要支持账号体系、服务端存储、多设备无感同步，最合适的总体方案不是“纯关系型数据库”或“纯非关系型数据库”二选一，而是：

- **以 `PostgreSQL` 作为核心主存储**
- **以 `JSONB` 承载结构化文档与画布状态**
- **以对象存储承载附件和大文件**
- **以本地 `SQLite` 承载桌面端离线缓存与同步队列**
- **以增量同步协议承载多端数据收敛**

### 2.2 对数据库问题的直接回答

对于 TopoMind 当前和可预见未来的数据形态：

- **适合使用关系型数据库作为主存储**
- **不适合把所有内容完全关系化**
- **不建议用 MongoDB 替代 PostgreSQL 作为主存储**
- **不建议用图数据库作为第一阶段主存储**
- **不建议继续沿用“云端 JSON 文件目录树”作为长期核心架构**

### 2.3 核心判断

TopoMind 的业务本质上是一个“带图视图的知识对象系统”，而不是一个“以复杂图计算为核心的图数据库产品”。  
它真正重要的是：

- 账号、工作区、权限与归属
- 知识库、卡片、文档、附件之间的稳定关系
- 排序、层级、移动、删除、恢复、一致性约束
- 多端同步下的版本控制与冲突处理
- 未来的分享、协作、统计、搜索与 AI 扩展能力

这些能力都更适合建立在关系型数据库之上。

## 3. 当前项目基线与问题背景

### 3.1 当前项目的真实存储模型

当前 TopoMind 的存储体系并不是“抽象意义上的本地存储”，而是非常明确的“文件系统目录即结构”模型：

- 工作目录是顶级数据边界
- `kbs/` 目录是知识库根
- 每个 KB 和卡片对应磁盘目录
- `_graph.json` 存储当前房间的子卡片与边
- `_docs/` 存储多类型结构化文档
- `_attach/` 存储附件
- `learning_stats/` 存储学习统计
- `_config.json` 存储工作区配置

这套模型在单机本地使用时非常直观，但在云端场景会带来以下问题：

- 业务主键与文件路径耦合过深
- 重命名、移动、恢复等操作过于依赖路径稳定性
- 多端同步下难以定义统一版本边界
- 云端难以直接复用“目录结构即数据结构”的表达方式
- 搜索、统计、权限、审计、协作都不适合围绕文件目录直接构建

### 3.2 当前代码层面的架构现实

项目当前已经具备一定的存储抽象：

- Renderer 通过 `StorageProvider/useStorage()` 使用统一存储入口
- 底层存在 `StorageBackend` 接口
- 本地文件读写通过 Electron preload + IPC + main process file service 完成

这意味着项目并非完全不能演进到云化，但目前抽象层仍以“本地路径模型”为核心，例如：

- `rootDir`
- `kbPath`
- `cardPath`
- `roomPath`
- `attachmentRef`

因此未来真正要演进的是两个层面：

1. **存储实现层**：从本地文件读写扩展到服务端存储与同步  
2. **数据身份层**：从路径驱动改为稳定 ID 驱动

### 3.3 当前产品的数据类型

TopoMind 的核心数据大致可分为六类：

1. 账号与工作区数据
2. 知识库与卡片层级数据
3. 图关系与画布布局数据
4. 智能笔记 / 思维导图 / 流程图等结构化文档
5. 附件与资源文件
6. 搜索索引、学习统计、同步状态等衍生数据

这六类数据的读写模式差异很大，因此底层设计必须采用“核心主存储 + 配套组件”的组合思路。

## 4. 设计目标

### 4.1 产品目标

云化后的 TopoMind 应支持：

- 用户登录与账号归属
- 工作区级数据隔离
- 多设备自动同步
- 尽量无感的数据更新
- 桌面端本地缓存与较好的离线体验
- 后续可扩展的分享、协作、权限和统计能力

### 4.2 技术目标

- 核心数据模型稳定，可长期演进
- 重要业务操作具备事务一致性
- 存储结构支持版本控制与冲突检测
- 前端与后端之间的数据协议清晰
- 本地缓存与远端主存储边界明确
- 文档类型可扩展，不因新增编辑器类型而推翻底层模型

### 4.3 设计原则

- **主键稳定**：所有核心实体以稳定 ID 为主键，不再以路径作为身份
- **元数据结构化**：关系和归属进入关系模型
- **复杂内容整体存储**：编辑器状态和画布状态以结构化 JSON 为主
- **文件单独存储**：大文件交给对象存储，不塞进数据库
- **同步优先可落地**：先解决版本控制和多端一致性，再考虑实时协作
- **渐进式迁移**：不做一次性推倒重来

## 5. 数据类型与存储方式判断

## 5.1 知识库 / 卡片层级

### 结论

**强烈建议使用关系型数据库存储。**

### 原因

知识库与卡片本质上是典型的业务实体：

- 有稳定归属关系
- 有父子层级
- 有排序
- 有删除/恢复
- 有移动
- 有显示名
- 后续可能有分享权限、标签、审计、最近访问记录

这种数据不适合长期用纯 JSON 文档存储，也不适合交给图数据库作为主模型。

### 建议存储方式

- `knowledge_bases` 表存 KB 元信息
- `cards` 表存卡片元信息
- `parent_id` 表示层级
- `sort_order` 表示同级顺序
- `deleted_at` 或单独 trash 机制表示软删除

---

## 5.2 图关系

### 结论

**第一阶段继续使用关系型数据库即可，不需要先上图数据库。**

### 原因

TopoMind 当前的图关系更偏向：

- 卡片之间的显式连接
- 有关系类型、权重、样式
- 主要用于可视化与交互

这与“复杂图推理平台”仍有明显差别。  
绝大多数这类产品在相当长时间内都可以通过普通边表建模：

- `source_card_id`
- `target_card_id`
- `relation`
- `weight`
- `style_json`

### 什么时候再考虑图数据库

只有当后续出现以下需求时，才建议认真评估 Neo4j 等图数据库：

- 多跳路径分析成为核心功能
- 大规模图推荐、相似路径发现成为核心卖点
- 查询模式大量依赖复杂图遍历
- 图算法性能成为主瓶颈

在此之前，引入图数据库会明显增加系统复杂度和运维成本，但收益有限。

---

## 5.3 智能笔记 / 思维导图 / 流程图

### 结论

**适合放在关系型数据库中，但内容主体应使用 `JSONB` 而不是完全拆表。**

### 原因

这些数据共同特点是：

- 有清晰的业务归属关系，例如属于某张卡片
- 有标题、类型、版本、更新时间等元数据
- 内部结构复杂且不断演进
- 不同文档类型的内部 schema 差异大

如果把每个 block、每个节点、每个 cell 都强拆成关系表，会导致：

- 表过多
- 写入复杂
- 版本迁移困难
- 编辑器升级成本高

### 推荐建模

使用统一文档表：

- 文档元数据字段使用普通关系型列
- 文档正文使用 `content_json JSONB`
- 通过 `type` 和 `schema_version` 区分不同编辑器类型

### 适配未来的好处

以后新增新的文档类型时，只需要：

- 新增前端编辑器
- 定义新的 schema
- 后端继续复用统一文档表

不需要因为增加“白板文档”或“时间线文档”就重构数据库。

---

## 5.4 画布布局与视图状态

### 结论

**适合单独作为“视图层数据”存储在 PostgreSQL 中，内容以 `JSONB` 为主。**

### 原因

画布布局不是核心知识实体，而是知识实体的一种展示状态。  
例如：

- 节点坐标
- 视图缩放
- 折叠状态
- 节点展开尺寸
- 边样式覆盖

这些数据：

- 会频繁更新
- 通常按房间整体保存
- 更像“view state”而不是“domain entity”

### 推荐建模

- `graph_layouts` 表
- 主体以 `layout_json` 或 `viewport_json` 存储
- 通过 `room_card_id` 或 `kb_id` 绑定到某个房间上下文

这样可以把“卡片本体”与“当前图视图”明确分离，避免数据职责混杂。

---

## 5.5 附件与大文件

### 结论

**不建议放入关系型数据库主体字段中，应使用对象存储。**

### 原因

附件数据的特点是：

- 容量较大
- 二进制格式多样
- 访问模式偏下载/预览
- 未来可能包含图片、PDF、音频、导出包等

如果直接把附件内容放进数据库：

- 数据库体积膨胀快
- 备份恢复成本变高
- 查询性能变差
- CDN 与签名访问能力受限

### 推荐组件

- AWS S3
- Cloudflare R2
- Supabase Storage
- MinIO

### 推荐建模方式

- 数据库存 `attachments` 元数据
- 对象存储保存真实文件
- 通过 `storage_key` 或 `bucket + object_key` 关联

---

## 5.6 搜索与 AI 检索

### 结论

**第一阶段不需要独立搜索引擎，可以先依赖 PostgreSQL；后期按规模外挂。**

### 原因

TopoMind 后续大概率会有：

- 卡片标题搜索
- 文档全文搜索
- 关系搜索
- AI 语义检索

如果一开始就上 Elasticsearch/OpenSearch，会过早增加复杂度。  
更合理的路线是：

- 先用 PostgreSQL 全文索引支持基础搜索
- 若后续全文规模和召回需求提高，再接 Meilisearch / Typesense
- 若要做语义搜索，则在 PostgreSQL 中使用 `pgvector` 起步

## 6. 为什么主存储应选择 PostgreSQL

## 6.1 与 TopoMind 需求的匹配点

`PostgreSQL` 对 TopoMind 的适配度高，原因在于它同时覆盖了以下需求：

- 强事务一致性
- 复杂关系查询
- 层级与排序处理
- JSONB 复杂文档内容存储
- 全文搜索
- 向量扩展
- 丰富索引能力
- 成熟生态与长期可维护性

## 6.2 相比 MongoDB

MongoDB 的优势在于灵活文档模型，但对 TopoMind 而言有几个问题：

- 工作区、权限、层级、移动、恢复等强约束业务不如关系型自然
- 长期同步一致性与事务治理不如 PostgreSQL 稳健
- 后续做统计、审计、复杂查询时关系型更直接

因此 MongoDB 更适合作为少数特殊子系统，而不是主存储。

## 6.3 相比图数据库

图数据库在复杂图遍历上有优势，但 TopoMind 当前并不以高阶图算法为核心。  
如果过早把主存储建立在图数据库上，会出现：

- 用户系统与权限模型不自然
- 文档系统、附件系统、同步系统都不顺手
- 运维与开发复杂度上升

因此图数据库最多作为后期增强组件，不适合第一阶段主底座。

## 6.4 相比继续使用云端文件系统

把当前本地目录树直接搬到云端，看起来迁移成本低，但长期问题很大：

- 难做并发控制
- 难做高质量搜索
- 难做权限与审计
- 难做结构化查询和统计
- 难做真正可靠的多端同步

因此“云端文件目录树”只适合作为导入导出形态，不适合作为长期核心架构。

## 7. 推荐的底层技术组合

## 7.1 标准推荐方案

### 核心主存储

- `PostgreSQL`

### 复杂结构化内容

- `PostgreSQL JSONB`

### 附件存储

- `S3 / R2 / Supabase Storage / MinIO`

### 桌面端本地缓存

- `SQLite`

### 基础搜索

- `PostgreSQL Full Text Search`

### 向量检索

- `pgvector`

### 实时与通知

- `WebSocket / Supabase Realtime / 自建事件系统`

## 7.2 不同团队阶段的推荐组合

### 方案 A：快速验证型

- 后端：Supabase
- 主库：PostgreSQL
- 认证：Supabase Auth
- 文件：Supabase Storage
- 实时：Supabase Realtime

适合：

- 人少
- 想快速上线
- 先验证产品方向

### 方案 B：长期产品化型

- 后端：NestJS
- ORM：Prisma 或 Drizzle
- 主库：PostgreSQL
- 缓存与队列：Redis
- 文件：S3 / R2 / MinIO
- 认证：自建 JWT + Refresh Token 或 Better Auth
- 实时：WebSocket / Socket.IO

适合：

- 追求长期可控
- 后续要加权限、分享、协作、审计
- 团队有持续工程投入

### 当前推荐

如果以 TopoMind 的长期演进为目标，推荐优先级如下：

1. 长期方案首选：`NestJS + PostgreSQL + 对象存储 + SQLite 缓存`
2. 快速 MVP 首选：`Supabase`

## 9. 客户端与同步架构建议

## 9.1 总体思路

云端版本不建议让前端直接变成“纯 API 调用器”，而应采用：

```text
Renderer UI
  -> Application Services
    -> Repository Interface
      -> Local Cache Repository
      -> Remote API Repository
      -> Sync Engine
```

## 9.2 核心原则

- 服务端是唯一真相源
- 客户端保留本地缓存
- 所有核心实体都有版本号
- 写操作先写本地缓存和同步队列，再异步推送远端
- 拉取更新时按版本合并到本地缓存

## 9.3 为什么要保留本地缓存

如果完全不做本地缓存，会出现：

- 打开速度受网络影响
- 大文档与图谱交互卡顿
- 断网无法编辑
- 附件与视图状态无法流畅访问

因此桌面端建议一定保留本地缓存层，并用 `SQLite` 作为主要承载。

## 9.4 同步协议建议

第一阶段推荐采用“版本号 + 增量拉取 + 乐观并发控制”的方案：

- 每个实体带 `version`
- 提交写入时附带客户端认知的 `version`
- 服务端校验版本是否匹配
- 若冲突则返回冲突错误和服务端最新版本
- 客户端按实体类型决定自动合并或人工提示

## 9.5 冲突策略建议

### 第一阶段建议

- 图布局：房间级覆盖写，必要时提示“已有其他设备更新”
- 卡片元数据：最后写入者生效或弹提示
- 文档：先按整文档冲突提示，不做 CRDT
- 附件：以新增为主，避免覆盖

### 后续增强

- 文档级差异合并
- 细粒度操作日志
- 局部字段级自动合并

---

## 10. 为什么暂不建议第一阶段做实时协作

多人实时协作与多设备同步并不是同一难度级别。  
TopoMind 若第一阶段就做实时协作，会额外引入以下复杂度：

- 文档操作流同步
- 图谱节点拖拽冲突
- 多端实时 presence
- CRDT / OT 架构
- 编辑器与画布的实时状态广播

这会显著提高开发和维护成本。  
因此更现实的路线应当是：

1. 先完成账号体系与云端主存储
2. 先完成多端自动同步
3. 再评估局部实时能力

## 11. 与当前代码架构的迁移关系

## 11.1 当前可复用部分

以下结构在未来可继续复用或演进：

- 统一的 `StorageProvider/useStorage()`
- 现有业务对统一存储入口的依赖方式
- 文档多类型抽象
- Electron preload / IPC 的桌面能力边界
- 前端的 Zustand 状态体系

## 11.2 当前需要重点重构的部分

### 一类：路径驱动的数据身份

当前多个模块以 `kbPath/cardPath/roomPath` 作为主键语义，未来需要逐步迁移为：

- `workspaceId`
- `kbId`
- `cardId`
- `documentId`

### 二类：存储接口过度本地化

当前很多接口天然假设“存在工作目录”和“存在本地路径”，未来需要拆分为：

- 云端数据访问接口
- 本地缓存接口
- 桌面平台能力接口

### 三类：学习统计与本地状态孤岛

学习统计、最近工作区、局部 UI 偏好、草稿缓存等，当前有些直接走本地能力，有些走 `localStorage`，后续需要重新划分：

- 哪些是账号级
- 哪些是设备级
- 哪些需要同步
- 哪些不需要同步

## 13. 风险与权衡

## 13.1 最大风险

- 过早把实时协作纳入第一阶段
- 不先清理路径身份模型就直接接后端
- 试图用单一数据库承载所有类型的数据
- 继续把对象文件当作核心数据结构

## 13.2 主要权衡

### 使用 PostgreSQL 的代价

- 需要更认真地建模
- 需要为复杂内容设计 JSON schema 与版本迁移策略
- 需要在关系与 JSON 之间控制边界

### 使用多组件组合的代价

- 系统组件更多
- 本地缓存与远端主存储需要同步协议
- 运维复杂度略高于单体数据库

### 收益

- 架构更稳定
- 更容易支持未来功能
- 多端同步与一致性基础更扎实
- 不容易在后期因底座错误而整体返工

## 14. 未决问题

以下问题需在正式实施前进一步确认：

1. 第一阶段是否要求完整离线编辑
2. 是否需要多人协作与分享能力
3. 学习统计是用户级同步还是设备级本地数据
4. 附件是否需要去重和跨文档复用
5. 图布局是按房间单份存储还是支持多视图
6. 是否要保留“导出为本地工作目录”的兼容能力
7. 当前本地工作目录如何迁移到云端数据模型

---

## 15. 最终建议

如果以 TopoMind 的长期产品化为目标，推荐明确采用以下路线：

- **主存储：`PostgreSQL`**
- **复杂内容：`JSONB`**
- **附件：对象存储**
- **桌面缓存：`SQLite`**
- **同步模式：版本号 + 增量同步 + 乐观并发控制**
- **第一阶段不做实时协作，不引入图数据库**

一句话概括：

> TopoMind 最适合采用“关系型数据库做骨架，JSONB 承载复杂内容，对象存储承载文件，SQLite 承载本地缓存”的组合架构，而不是寻找一个可以包打天下的单一数据库。

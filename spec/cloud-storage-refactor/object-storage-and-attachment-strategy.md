## 1. 文档目标

本文档用于把 TopoMind 云同步重构中的“附件系统”单独拆出来，细化为可实施方案，重点回答以下问题：

- 为什么附件不能继续沿用“本地目录里的普通文件”作为长期主模型
- 对象存储、数据库元数据、同步协议、本地缓存、桌面能力应该如何分层
- 附件上传、下载、预览、删除、恢复应遵循什么流程
- 对象存储 key 应该如何设计，才能兼顾可维护性、迁移性与成本
- 本地缓存和系统打开能力应该如何与云端附件协同
- 当前本地工作目录中的附件如何迁移到新架构

本文档默认针对：

- Electron 桌面端
- 单用户多设备同步优先
- 第一阶段不做多人实时协作
- 服务端为唯一真相源

## 2. 设计摘要

### 2.1 最终结论

TopoMind 的附件系统建议明确拆成五层：

- **对象存储层**：保存真实二进制文件
- **附件元数据层**：保存附件归属、类型、大小、hash、版本等结构化信息
- **上传下载协议层**：负责票据、签名 URL、提交确认、权限校验
- **本地文件缓存层**：负责下载缓存、预览缓存、临时文件
- **桌面能力层**：负责系统打开、在 Finder 中显示、导出到本地

### 2.2 第一阶段目标

第一阶段附件系统要确保六件事：

1. 附件本体不进入主数据库  
2. 附件元数据进入统一同步体系  
3. 上传采用对象存储直传或近似直传  
4. 下载和预览通过签名 URL 或服务端受控地址完成  
5. 本地可缓存最近使用附件，便于桌面打开  
6. 删除、恢复、迁移都与核心实体模型保持一致  

### 2.3 第一阶段不做

- 不做完整的企业级文件权限系统
- 不做复杂秒传网络和跨工作区全局去重
- 不做大文件协同编辑
- 不做完整媒体处理流水线
- 不做附件版本历史浏览 UI

## 3. 为什么附件必须独立建模

当前本地模式里，附件更像“卡片目录中的文件”。  
但云端阶段如果继续把附件当普通文件处理，会马上遇到问题：

- 无法自然表达权限和归属
- 无法稳定做预览与下载授权
- 无法处理多设备缓存与清理
- 无法为迁移、恢复、审计保留结构化元数据
- 无法在数据库层做合理查询和关联

因此附件必须从一开始就明确区分：

- **附件本体**
- **附件元数据**

## 4. 分层边界

## 4.1 对象存储层

职责：

- 保存真实文件内容
- 提供上传和下载入口
- 支持签名 URL 或受控访问

不负责：

- 业务归属关系
- 卡片、文档、工作区权限语义
- 同步事件

## 4.2 附件元数据层

职责：

- 保存 `attachment.id`
- 保存所属 `workspace_id / card_id / document_id`
- 保存 `file_name / mime_type / size_bytes / sha256`
- 保存 `storage_provider / storage_bucket / storage_key`
- 保存软删除、版本号、时间戳

不负责：

- 文件本体
- 本地缓存路径

## 4.3 上传下载协议层

职责：

- 申请上传票据
- 提交上传确认
- 生成下载 URL
- 校验权限和签名时效

## 4.4 本地文件缓存层

职责：

- 保存最近下载的文件
- 保存图片缩略图和预览临时文件
- 记录缓存命中、访问时间和清理策略

## 4.5 桌面能力层

职责：

- 系统默认应用打开
- 在 Finder 中显示
- 导出到用户指定目录

### 关键原则

桌面能力层不应成为附件真相源，只消费本地缓存文件。

## 5. 组件选型建议

## 5.1 推荐对象存储组件

优先推荐以下对象存储之一：

- `AWS S3`
- `Cloudflare R2`
- `Supabase Storage`
- `MinIO`

## 5.2 选择标准

附件存储组件至少应满足：

- 支持预签名上传
- 支持预签名下载
- 支持分桶管理或逻辑隔离
- 支持合理的生命周期规则
- 支持按对象 key 访问

## 5.3 当前推荐

若你走快速落地路线：

- `Supabase Storage`

若你走长期产品化路线：

- `S3 / R2 / MinIO`

### 原因

- 和 `NestJS + PostgreSQL` 组合更自然
- 未来更容易接入独立 CDN、清理任务和媒体处理

## 6. 附件实体模型建议

## 6.1 元数据模型

附件元数据延续已有 schema 方向，建议至少包含：

- `id`
- `workspace_id`
- `card_id`
- `document_id`
- `file_name`
- `mime_type`
- `size_bytes`
- `storage_provider`
- `storage_bucket`
- `storage_key`
- `sha256`
- `meta_json`
- `version`
- `created_at`
- `updated_at`
- `deleted_at`

## 6.2 `meta_json` 建议放什么

建议放弱约束扩展信息，例如：

- 图片宽高
- PDF 页数
- 视频时长
- 缩略图状态
- 原始导入路径
- 迁移来源信息

### 不建议放什么

- 高频过滤字段
- 安全关键字段
- 必须参与权限判断的字段

## 6.3 归属原则

第一阶段建议：

- 主归属为 `card_id`
- `document_id` 只表达来源或挂载上下文

### 原因

- 与现有产品模型更接近
- 避免文档移动时附件归属过早复杂化

---

## 7. 对象存储 key 设计

## 7.1 设计原则

对象 key 应满足：

- 稳定且可重建
- 不直接泄露业务敏感信息
- 支持按工作区或时间分区
- 不依赖原始文件名唯一性
- 便于清理与迁移

## 7.2 推荐 key 结构

第一阶段建议：

```text
attachments/{workspaceId}/{yyyy}/{mm}/{attachmentId}-{safeFileName}
```

例如：

```text
attachments/ws_123/2026/06/att_456-image.png
```

## 7.3 为什么不建议把 cardPath 放进 key

因为：

- 路径未来不再是主身份
- 重命名或移动卡片会导致 key 语义脆弱
- 会把旧路径模型继续写进云架构

## 7.4 是否要把 hash 放进 key

可以，但第一阶段不强制。

### 推荐折中

- 主 key 仍以 `attachmentId` 为主
- `sha256` 单独入库

### 原因

- 避免对象 key 和去重策略强耦合
- 未来若变更 hash 算法，不影响对象寻址

## 8. 上传策略

## 8.1 第一阶段推荐流程

第一阶段推荐标准双阶段流程：

1. 客户端申请上传票据  
2. 服务端校验权限并返回上传目标  
3. 客户端上传二进制到对象存储  
4. 客户端调用 `commit` 提交元数据  
5. 服务端创建 `attachments` 记录并写入同步事件  

## 8.2 为什么不能先建附件记录再慢慢上传

因为会导致：

- 数据库里出现大量悬空附件
- 用户以为已上传成功
- 清理和恢复都复杂

所以更稳的做法是：

- 先上传文件
- 再提交元数据

## 8.3 上传票据建议字段

服务端返回的上传票据建议包含：

- `uploadUrl`
- `method`
- `headers`
- `storageKey`
- `expiresAt`
- `maxSizeBytes`
- `allowedMimeTypes`

## 8.4 大文件策略

第一阶段可以分两档：

- 小文件：单次上传
- 大文件：视对象存储能力决定是否支持 multipart

### 推荐现实策略

- 第一阶段先支持单次上传
- 后续再补 multipart

### 原因

- 能更快落地
- 配合桌面端常见使用场景已足够

## 8.5 客户端上传任务状态

建议 `attachment_upload_jobs` 至少包含：

- `pending`
- `uploading`
- `uploaded`
- `committing`
- `done`
- `failed`
- `cancelled`

---

## 9. 提交确认策略

## 9.1 `commit` 的职责

`commit` 接口必须负责：

- 校验上传结果是否合理
- 记录附件元数据
- 建立 card/document 归属关系
- 追加同步事件

## 9.2 `commit` 请求建议字段

- `workspaceId`
- `cardId`
- `documentId`
- `fileName`
- `mimeType`
- `sizeBytes`
- `storageKey`
- `sha256`
- `idempotencyKey`

## 9.3 幂等要求

`commit` 必须支持幂等。

### 原因

- 上传后网络抖动很常见
- 用户重试不能生成多条重复附件记录

---

## 10. 下载与预览策略

## 10.1 下载原则

下载附件不应通过同步事件直接传输文件本体。

同步层只负责：

- 元数据
- 版本
- 删除状态
- 可下载身份

## 10.2 下载入口建议

推荐两种模式之一：

### 模式 A：服务端返回签名 URL

优点：

- 最简单
- 对象存储压力可直接承接

代价：

- URL 生命周期要管理

### 模式 B：业务服务做受控转发

优点：

- 权限完全由业务服务掌控

代价：

- 后端带宽和实现复杂度更高

### 第一阶段推荐

更推荐模式 A。

## 10.3 预览入口建议

不同附件类型建议不同处理：

- 图片：直接签名 URL 或下载后本地预览
- PDF：优先下载缓存后本地预览，或受控 URL 内嵌
- 文本：可下载后读取本地内容
- 音视频：按体积决定流式预览或下载后打开

## 10.4 URL 生命周期

签名 URL 应具备有限时效，例如：

- 5 分钟
- 15 分钟
- 1 小时

### 推荐

- 下载链接短时有效
- 客户端不要长期持久化签名 URL

---

## 11. 本地缓存与桌面打开

## 11.1 本地缓存原则

桌面端所有“系统打开”能力，都应先命中本地缓存文件。

### 流程建议

1. 检查本地缓存是否存在  
2. 若不存在则下载到缓存目录  
3. 校验下载完整性  
4. 再调用系统默认应用打开  

## 11.2 缓存命名建议

建议沿用本地缓存文档中的思路：

```text
attachments/workspace-{workspaceId}/{attachmentId}-{sha256}.{ext}
```

## 11.3 是否允许用户“另存为”

建议支持，但语义应是：

- 从缓存文件或下载文件导出
- 不是把缓存目录直接暴露为用户工作目录

## 11.4 Finder 中显示

“在 Finder 中显示”应解释为：

- 如果本地缓存文件存在，则显示缓存文件
- 如果缓存不存在，先下载再显示

### 关键点

这已经不是“显示服务器上的原始路径”，而是“显示本地缓存副本”。

## 12. 删除与恢复策略

## 12.1 删除语义

第一阶段建议对附件采用软删除元数据 + 延迟清理对象本体的策略。

### 原因

- 便于恢复
- 避免误删对象文件
- 有利于迁移和审计

## 12.2 删除流程

建议流程：

1. 删除附件元数据关系  
2. 标记 `deleted_at`  
3. 推进 `version`  
4. 写入 `change_events`  
5. 对象存储本体由后台清理任务延迟处理  

## 12.3 恢复流程

若对象本体尚未被清理，可直接：

- 清空 `deleted_at`
- 推进版本
- 恢复引用可见性

若对象本体已清理，则恢复应失败并提示不可恢复。

## 12.4 是否立即删除对象文件

第一阶段不建议立即删。

### 更推荐

- 延迟删除
- 批量清理
- 与软删除窗口联动

---

## 13. 引用与文档嵌入策略

## 13.1 文档中如何表达附件引用

第一阶段不建议直接把文档正文永久写死成签名 URL。

### 推荐表达方式

- 文档中保留逻辑引用
- 渲染时再解析为当前可用的下载或预览地址

## 13.2 推荐逻辑引用形式

可以考虑在 `content_json` 中显式存：

- `attachmentId`
- `fileName`
- `mimeType`

而不是只存一个裸 URL。

## 13.3 为什么不建议永久 URL

因为：

- URL 可能过期
- 存储域名可能变化
- 权限模型未来可能变化

---

## 14. 迁移策略

## 14.1 与本地工作目录迁移的关系

迁移阶段附件应遵循：

- 先导入结构化实体
- 再导入附件
- 再回填文档或封面引用

## 14.2 旧本地路径保留建议

建议在附件元数据或迁移日志中保留：

- `legacy_relative_path`
- `legacy_source_document`
- `legacy_card_path`

### 用途

- 调试迁移问题
- 迁移报告审计
- 导出兼容

## 14.3 Markdown 图片引用兼容

若旧 Markdown 使用相对路径：

- 迁移时先提取引用关系
- 建立 `path -> attachmentId` 映射
- 渲染层通过 attachment 解析

### 第一阶段原则

宁可保守保留原始引用信息，也不要在迁移期做高风险的正文批量改写。

## 15. 权限与安全

## 15.1 权限边界

附件访问权限必须依附于业务实体权限，而不是只依赖对象存储公开地址。

### 最小要求

- 只有有权访问该工作区的用户，才可申请下载 URL
- 只有有权编辑对应 card/document 的用户，才可上传和删除附件

## 15.2 URL 安全

客户端不应：

- 长期存储签名 URL
- 在日志中直接打印完整私有 URL
- 把下载 URL 当成永久链接分享

## 15.3 MIME 与大小校验

服务端应校验：

- MIME 白名单或黑名单
- 文件大小上限
- 扩展名与 MIME 的基本一致性

### 第一阶段即使不做病毒扫描，也应至少做基础校验。

---

## 16. 去重与存储成本策略

## 16.1 是否要做去重

第一阶段不建议做复杂全局去重系统。

### 原因

- 会显著增加引用关系复杂度
- 删除和恢复语义更难
- 对第一阶段价值有限

## 16.2 可以保留哪些去重准备

建议保留：

- `sha256`
- `size_bytes`

这样后续若要做去重或秒传，会更容易演进。

## 16.3 存储成本控制

第一阶段更现实的控制手段是：

- 限制单文件大小
- 限制工作区总附件容量
- 用文件缓存清理降低本地占用
- 用对象生命周期规则清理长期已删除对象

---

## 17. 缩略图与媒体处理

## 17.1 第一阶段建议

第一阶段不要强依赖完整媒体处理系统。

### 最务实策略

- 图片：客户端或简单服务端生成缩略图
- PDF：先不做复杂预渲染
- 视频：先不做转码

## 17.2 若后续要增强

可逐步补：

- 异步缩略图任务
- PDF 首图预览
- 视频转码与截图

但这些不应阻塞第一阶段附件主链路。

---

## 18. 与当前代码重构的衔接

## 18.1 现有桌面能力如何迁移

当前附件相关能力里，像“系统打开”“在 Finder 中显示”这类功能，应从“存储后端接口”中拆出来，归入平台能力层。

### 原因

- 它们不是附件真相源的一部分
- 它们只在桌面端有意义
- 云端和 Web 端无法复用同样语义

## 18.2 UI 层不应直接理解对象存储

UI 层最好只拿到：

- `attachment metadata`
- `preview state`
- `download status`
- `open action`

而不直接理解 bucket、签名 URL、存储 provider 等底层细节。

## 18.3 同步层只同步元数据

必须坚持：

- `attachments` 元数据参与 `change_events`
- 对象文件本体不参与事件流

---

## 19. 推荐实施顺序

建议按以下顺序落地：

1. 先确定附件元数据模型  
2. 先完成对象存储 key 规则  
3. 再实现上传票据与 `commit` 接口  
4. 再实现下载 URL 与本地缓存  
5. 再实现系统打开、Finder 显示、清理任务  
6. 最后补缩略图和高级媒体处理  

### 为什么这样排

- 先把核心链路打通
- 再补桌面体验
- 最后再做增强能力

---

## 20. 风险与权衡

## 20.1 最大风险

- 把对象存储 key 和路径模型绑定过深
- 让签名 URL 进入长期数据
- 把附件本体混入同步事件流
- 过早做复杂去重和媒体处理

## 20.2 当前方案的取舍

### 选择“元数据同步 + 本体直传”

代价：

- 上传流程比普通实体更复杂

收益：

- 大文件能力更稳
- 更符合对象存储模型

### 选择“软删除后延迟清理对象”

代价：

- 需要后台清理任务

收益：

- 恢复语义更好
- 误删风险更低

### 选择“不做复杂全局去重”

代价：

- 存储成本可能略高

收益：

- 第一阶段系统复杂度更低
- 删除恢复模型更清晰

## 21. 未决问题

正式实施前，仍需确认以下问题：

1. 第一阶段单文件大小上限是多少  
2. 是否需要在工作区维度设置附件容量上限  
3. 图片缩略图是在客户端生成还是服务端生成  
4. 是否支持大文件 multipart 上传  
5. 退出登录时本地附件缓存是否全部清理  
6. 是否要为附件预留病毒扫描或安全审核状态  
7. 文档内容里最终采用哪种 attachment 逻辑引用格式

## 22. 最终建议

TopoMind 附件系统最关键的不是“把文件放到云上”，而是：

- 本体和元数据彻底分层
- 元数据进入统一实体模型和同步体系
- 本体交给对象存储
- 预览和系统打开依赖本地缓存副本
- 签名 URL 只做临时访问凭证

一句话概括：

> 用对象存储保存文件，用数据库保存附件身份和归属，用同步系统传播元数据，用本地缓存承接桌面预览与系统打开，这才是 TopoMind 云端附件架构的稳定形态。

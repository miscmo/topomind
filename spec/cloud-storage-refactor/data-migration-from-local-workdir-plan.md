## 1. 文档目标

本文档用于回答 TopoMind 从当前“本地工作目录”迁移到“账号 + 云端工作区 + 本地缓存”的过程中，数据应该如何迁移，重点回答以下问题：

- 当前本地工作目录里的每一类文件应该映射到哪些云端实体
- 迁移时哪些旧 ID 可以复用，哪些必须重建
- 如何尽量减少路径模型对迁移的污染
- 如何支持用户导入已有工作目录
- 迁移失败时如何恢复
- 迁移期间如何兼容旧版本地模式
- 哪些内容适合一次性导入，哪些应延后或弱迁移

本文档默认针对：

- 已有大量本地工作目录的 TopoMind 用户
- 第一阶段单用户多设备云同步
- 服务端真相源 + 客户端本地缓存

## 2. 设计摘要

### 2.1 最终结论

TopoMind 的迁移不应理解为“把目录原样上传到服务器”，而应理解为：

- **解析本地工作目录**
- **提取稳定业务实体**
- **建立云端 ID 模型**
- **按实体而不是按路径导入**
- **保留必要的路径映射用于兼容与回溯**

### 2.2 第一阶段推荐路线

第一阶段最稳妥的迁移路径是：

1. 先做“本地工作目录导入器”  
2. 先把旧数据转换成云端实体快照  
3. 先按工作区级一次性导入  
4. 导入完成后再进入正常增量同步模式  

### 2.3 第一阶段不做

- 不做“边修改本地目录边实时双向同步”
- 不做直接把 `_graph.json` 当作长期云端结构
- 不做导入中途的多人协作合并
- 不做复杂的目录级增量迁移算法
- 不做旧本地目录和新云端模型长期双主并存

## 3. 当前本地模型与目标模型

## 3.1 当前本地模型的关键事实

根据当前 [SPEC.md](file:///Users/lhg/Documents/topomind/spec/SPEC.md)，本地工作目录核心结构包括：

- 根目录 `_config.json`
- `kbs/` 目录下的知识库目录
- 每个 KB 或卡片目录下的 `_graph.json`
- 每个卡片目录下的 `README.md`
- 图片、附件或相关资源目录
- `logs/`
- 其他本地辅助文件

### 当前模型的核心特征

- 目录即层级
- 路径深度即业务层级
- `_graph.json` 既承载子节点关系，也承载布局状态
- `README.md` 承载文档正文
- 一部分节点已有本地唯一 key
- 但业务层和 UI 仍大量使用路径语义

## 3.2 目标云端模型的关键事实

根据已有云端文档，目标模型核心实体包括：

- `workspace`
- `knowledge_base`
- `card`
- `card_edge`
- `graph_layout`
- `document`
- `attachment`
- `workspace_config`

### 目标模型的核心特征

- 稳定 ID 驱动
- 路径只作为兼容信息或导出信息
- 文档、布局、附件分层存储
- 云端为真相源

---

## 4. 迁移原则

迁移方案建议坚持以下原则：

- **先提取实体，再上传**
- **优先复用已有稳定本地 ID**
- **绝不把路径当成长期主键继续带入云端**
- **迁移过程可重试、可回滚、可审计**
- **导入完成后进入云端版本化模型**
- **旧本地目录可作为导入来源，但不再作为新架构核心存储**

## 5. 映射关系

## 5.1 顶层映射

建议映射如下：

| 本地来源 | 云端目标 |
|---|---|
| 工作目录 | `workspace` |
| 根 `_config.json` | `workspace_config` |
| `kbs/{kb-dir}` | `knowledge_base` |
| 目录树中的每个卡片目录 | `card` |
| `_graph.json.edges` | `card_edge` |
| `_graph.json.children + zoom + pan` | `graph_layout` |
| `README.md` | `document(type=smart)` |
| 图片/附件目录 | `attachment` + object storage |
| `logs/` | 默认不迁移或仅做离线保留 |

## 5.2 `knowledge_base` 映射

本地每个顶层 KB 目录映射为一个 `knowledge_base`。

### 推荐字段来源

- `name`：目录显示名或目录对应显示名
- `sort_order`：根 `_config.json.orders`
- `cover_attachment_id`：若存在封面文件则在附件导入后回填

## 5.3 `card` 映射

每个卡片目录映射为一个 `card`。

### 推荐字段来源

- `id`：优先复用 `_graph.json.children` 中已有 card key
- `kb_id`：所属 KB
- `parent_id`：父目录对应 card
- `name`：目录在父 `_graph.json.children[key].name` 中的显示名
- `meta_json`：可存导入来源信息和旧路径信息

## 5.4 `graph_layout` 映射

本地每个目录下的 `_graph.json` 不应整体照搬为一个“通用 JSON 文件”，而应拆为：

- `children` 的布局信息 -> `graph_layout.layout_json`
- `zoom/pan` -> `graph_layout.viewport_json`
- `edges` -> `card_edges`

### 关键点

- `graph_layout` 只表达展示状态
- `card_edges` 表达语义关系
- 不能把两者继续混在一个长期云端对象里

## 5.5 `document` 映射

第一阶段建议把每个 `README.md` 导入为：

- `document.type = smart`
- `document.title` 可用卡片名或默认文档标题
- `document.content_json` 由 Markdown 导入器转换后的结构化结果

### 如果当前尚未有结构化文档树

可以先采用：

- 每卡片一篇主文档
- 迁移后再逐步支持一个卡片下多文档

## 5.6 `attachment` 映射

本地图片和附件文件建议映射为：

- 对象存储中的真实文件
- `attachments` 表中的元数据记录

### 推荐附加元数据

- 来源旧路径
- 原始相对引用路径
- 所属 card
- 可能的来源 document

## 6. ID 策略

## 6.1 哪些 ID 可复用

从现有规范看，本地 `_graph.json.children` 已经存在类似：

- `card-23223xaaf`

这类 key 有明显“稳定 ID”倾向。  
因此迁移时建议：

- **优先复用现有 card key 作为 `card.id`**

### 好处

- 减少旧引用断裂
- 降低路径到 ID 迁移成本
- 有利于导入日志和问题排查

## 6.2 哪些 ID 需要新建

以下对象通常建议新建云端 ID：

- `workspace.id`
- `knowledge_base.id`
- `document.id`
- `attachment.id`
- `graph_layout.id`
- `card_edge.id`

### 原因

- 旧模型里这些实体往往没有统一稳定主键
- 直接基于路径生成会继续绑定路径语义

## 6.3 路径映射建议

迁移时建议保留辅助映射：

- `legacy_relative_path`
- `legacy_parent_relative_path`
- `legacy_workdir_fingerprint`

### 用途

- 调试导入问题
- 冲突排查
- 迁移校验
- 导出兼容

### 但必须明确

这些字段只作为兼容或审计信息，不得重新升级为业务主键。

## 7. 导入模式建议

## 7.1 推荐模式：一次性工作区导入

第一阶段最推荐：

- 用户选择本地工作目录
- 系统解析完整目录
- 生成导入预览
- 用户确认后一次性导入为一个云端工作区

### 原因

- 用户心智简单
- 容易做一致性校验
- 比目录级增量迁移更稳

## 7.2 不推荐模式：长期目录镜像同步

不建议做：

- 本地目录改了，云端自动感知
- 云端改了，本地目录自动回写

### 原因

- 会把新架构再次绑回路径和文件系统
- 冲突边界很难定义
- 实现和排障成本极高

## 7.3 可选补充模式：单 KB 导入

若用户已有超大工作目录，也可支持：

- 以单 KB 为粒度导入

但建议这是增强能力，不是第一阶段默认流程。

## 8. 迁移前校验

正式导入前，建议导入器做以下校验：

- 根目录是否合法
- `kbs/` 是否存在
- `_config.json` 是否可解析
- `_graph.json` 是否为合法 JSON
- `children` 中的 key 和目录是否能对上
- 边引用的 source/target 是否存在
- `README.md` 是否可读取
- 是否存在明显重复或损坏的 ID

## 8.1 发现问题时的处理等级

建议把问题分三类：

### 致命错误

- 根目录结构错误
- 关键 JSON 无法解析
- 大量节点缺失导致结构无法建立

### 可恢复错误

- 部分卡片缺 README
- 部分布局字段缺失
- 个别图片丢失

### 提示级问题

- 显示名为空，需回退目录名
- 封面文件缺失
- 排序配置不完整

## 9. 导入执行流程

## 9.1 推荐总体流程

```text
选择本地工作目录
  -> 基础校验
  -> 扫描目录树
  -> 构建中间迁移模型
  -> 生成导入预览
  -> 用户确认
  -> 创建云端 workspace
  -> 导入 knowledge_bases
  -> 导入 cards
  -> 导入 card_edges
  -> 导入 graph_layouts
  -> 导入 documents
  -> 上传 attachments
  -> 回填附件引用
  -> 写入导入报告
```

## 9.2 为什么要有“中间迁移模型”

不建议扫描一个文件就直接写一次远端。

### 推荐先构建中间模型

例如：

- `ParsedWorkspace`
- `ParsedKB`
- `ParsedCard`
- `ParsedDocument`
- `ParsedAttachment`

### 好处

- 能先做完整校验
- 能统一处理 ID 映射
- 能先给用户看导入预览
- 出错时更容易回滚

## 9.3 导入顺序建议

导入顺序建议严格分层：

1. `workspace`
2. `workspace_config`
3. `knowledge_bases`
4. `cards`
5. `card_edges`
6. `graph_layouts`
7. `documents`
8. `attachments`
9. 回填封面和附件关联

### 原因

- 下游实体大量依赖上游 ID
- 附件通常最慢、最容易失败
- 把附件放后面更利于先完成核心知识结构导入

## 10. 中间迁移模型建议

## 10.1 工作区级模型

```ts
interface ParsedWorkspace {
  legacyRootPath: string
  config: ParsedWorkspaceConfig | null
  kbs: ParsedKB[]
  warnings: ParsedWarning[]
}
```

## 10.2 KB 级模型

```ts
interface ParsedKB {
  legacyPath: string
  kbName: string
  sortOrder: number
  cards: ParsedCard[]
  layouts: ParsedGraphLayout[]
  attachments: ParsedAttachment[]
}
```

## 10.3 卡片级模型

```ts
interface ParsedCard {
  legacyPath: string
  cardId: string
  parentCardId: string | null
  kbId: string
  displayName: string
  markdownPath: string | null
  childCardIds: string[]
}
```

### 说明

这个中间层不一定要完全按这个接口实现，但建议明确“解析阶段模型”和“远端落库模型”是两回事。

## 11. 文档迁移策略

## 11.1 第一阶段 Markdown 导入策略

当前 `README.md` 是文档主体。  
第一阶段建议：

- 先把 Markdown 作为唯一文档来源
- 通过导入器转成 `document.content_json`
- 默认生成一篇 `smart` 类型文档

## 11.2 Markdown 到结构化 JSON 的两种路线

### 路线 A：轻转换

- 标题、段落、列表、代码块做基础结构化
- 未识别部分作为原始块保留

### 路线 B：包一层原始 Markdown

- `content_json` 中保留原始 Markdown 文本
- 迁移后第一次打开时再惰性转换

### 第一阶段推荐

更推荐路线 B 或“B 为主，A 为辅”。

### 原因

- 风险更低
- 不容易在导入期损坏文档语义
- 后续可以逐步升级转换器

## 11.3 文档标题策略

建议优先顺序：

1. 文档显式标题  
2. 卡片显示名  
3. 目录名

## 12. 布局与边迁移策略

## 12.1 `_graph.json.children`

`children` 中的内容要拆成两部分理解：

- 子卡片身份与显示名
- 子卡片在当前房间中的位置与布局信息

### 迁移建议

- 身份与层级进入 `cards`
- 位置、展开状态等进入 `graph_layout.layout_json`

## 12.2 `_graph.json.edges`

每条边迁移为一条 `card_edge`。

### 建议保留字段

- `source`
- `target`
- `relation`
- `weight`

### 建议新增导入元数据

- 来源房间路径
- 来源旧 graph 文件路径

## 12.3 `zoom/pan`

迁移为 `graph_layout.viewport_json`。

### 注意

- 这属于视图状态，不属于卡片实体属性
- 不应因为迁移方便就塞进 `cards.meta_json`

---

## 13. 附件迁移策略

## 13.1 第一阶段附件原则

附件迁移建议单独处理，不要和结构化实体导入完全混在一个事务中。

### 原因

- 文件上传慢
- 失败率更高
- 容量不稳定

## 13.2 推荐附件导入流程

1. 扫描本地附件文件  
2. 建立 `ParsedAttachment` 列表  
3. 先完成结构化实体导入  
4. 再批量上传附件  
5. 上传成功后回填 `attachments` 记录和引用关系  

## 13.3 图片引用更新

如果 Markdown 中有相对路径图片引用，迁移后必须处理：

- 原始相对路径
- 新 attachment ID
- 新预览或下载 URL 生成方式

### 推荐策略

- 迁移阶段先保留原始引用信息
- 文档渲染层按 attachment 引用表解释
- 不强依赖把 Markdown 原文直接替换成最终 URL

## 14. 迁移过程中的兼容策略

## 14.1 旧工作目录是否继续保留

建议保留。

### 原因

- 它是用户可见的原始数据资产
- 可作为迁移失败时的安全来源
- 也有利于用户逐步过渡到云端版

## 14.2 迁移完成后是否继续把旧目录当活跃数据源

不建议。

### 推荐语义

- 旧目录是“导入来源”
- 云端工作区是“迁移后的真相源”
- 本地 `SQLite` 是“缓存层”

## 14.3 是否需要导出回本地目录

建议保留“导出为本地工作目录”的能力，但这应是：

- 导出功能
- 备份功能
- 兼容功能

而不是新架构的核心存储方式。

## 15. 迁移失败与回滚

## 15.1 导入前失败

如果在预扫描或预校验阶段失败：

- 不创建云端工作区
- 直接返回错误报告

## 15.2 导入中途失败

建议采用“导入会话”概念：

- `migration_job`
- `migration_report`

### 若中途失败

- 记录已完成阶段
- 记录失败实体和原因
- 支持从最近安全阶段重试

## 15.3 是否需要硬回滚

第一阶段不必强求所有内容做跨附件上传的全局硬事务回滚。

### 更现实的策略

- 结构化实体阶段尽量事务化
- 附件阶段允许部分失败并单独重试
- 未完成的工作区标记为“导入未完成”

## 15.4 用户侧恢复建议

迁移失败时应向用户明确展示：

- 哪一步失败
- 是否已创建云端工作区
- 是否需要重试
- 本地原始目录未被修改

## 16. 数据校验与迁移报告

## 16.1 迁移报告应包含的内容

建议生成导入报告，至少包括：

- 工作目录路径
- 导入时间
- 导入用户
- KB 数量
- 卡片数量
- 边数量
- 文档数量
- 附件数量
- 警告数量
- 失败项列表

## 16.2 导入后校验

导入完成后建议做最小一致性校验：

- KB 数量是否一致
- 卡片数量是否一致
- 边数量是否大体一致
- 是否存在孤儿卡片
- 是否存在缺失文档
- 是否存在未回填附件引用

## 16.3 可选校验增强

后续可增加：

- 目录树和云端树的对比摘要
- 抽样文档内容比对
- 附件 hash 校验

## 18. 与当前代码重构的衔接

## 18.1 为什么迁移器不能直接复用旧业务路径模型

因为旧业务模型里：

- 路径不仅是定位方式，还是很多状态的主键
- 直接复用会把旧耦合再次带入云端架构

所以迁移器应该是：

- 读取旧结构
- 解析旧模型
- 输出新实体

而不是继续传播旧路径语义。

## 18.2 迁移器适合放在哪一层

建议迁移器分三层：

- `LegacyWorkdirScanner`
- `MigrationMapper`
- `CloudImportService`

### 职责

- `Scanner`：读取目录和文件
- `Mapper`：生成中间迁移模型
- `CloudImportService`：按新协议落远端

## 18.3 与本地缓存层的关系

迁移成功后建议：

- 直接把云端返回实体写入本地 `SQLite`
- 不再从旧目录重新生成本地缓存

这样可以避免“双缓存来源”。

## 20. 风险与权衡

## 20.1 最大风险

- 误把路径继续带成主键
- 过早追求目录级双向同步
- 在导入阶段就做过重的文档结构转换
- 附件和正文引用关系处理不稳

## 20.2 当前方案的取舍

### 选择“一次性导入”而非“长期目录同步”

代价：

- 用户需要有一次明确迁移动作

收益：

- 架构边界清晰
- 后续实现和维护难度大幅降低

### 选择“优先复用 card key”

代价：

- 要对旧数据质量有一定校验

收益：

- 迁移更稳
- 兼容成本更低

### 选择“Markdown 轻转换或惰性转换”

代价：

- 第一阶段文档模型可能不够完美

收益：

- 降低导入期风险
- 更容易保证文档内容不丢

## 21. 未决问题

正式实施前，仍需确认以下问题：

1. 现有所有卡片目录是否都能稳定拿到本地 card key  
2. `README.md` 是否永远作为每卡片默认主文档  
3. 图片和附件当前在所有分支目录中的真实存放规则是否完全统一  
4. 迁移后是否要保留“继续打开旧本地工作目录”的入口  
5. 导入失败后是否允许继续在同一云端工作区内补导入  
6. 是否需要为导入过程设计服务端 `migration_jobs` 表  
7. 是否要在 UI 中显式展示“本地目录已导入云端”的映射关系

## 22. 最终建议

TopoMind 最稳的迁移路线不是“把文件系统搬上云”，而是：

- 读取旧目录
- 提取稳定实体
- 复用已有 card key
- 生成云端 ID 关系
- 分层导入结构、文档和附件
- 导入完成后彻底切换到云端真相源

一句话概括：

> 旧本地工作目录应成为云端时代的“导入来源和备份形态”，而不应继续扮演未来主存储；迁移的关键不是上传文件，而是把路径世界翻译成稳定 ID 世界。

**项目**：TopoMind — 可漫游拓扑知识大脑

---

## 1. 文档目标

本文档用于把 TopoMind 云同步重构中的“客户端本地缓存层”进一步细化为可实施方案，重点回答以下问题：

- 为什么桌面端必须保留本地缓存
- 本地缓存应该分几层，各自存什么
- 哪些数据需要镜像到 `SQLite`
- 哪些数据应该保留为设备级状态，不参与云同步
- 离线状态下允许什么，不允许什么
- 本地缓存损坏、过大、过旧时应如何恢复与清理
- 附件下载、预览和系统打开时，本地文件缓存怎么设计

本文档默认适用范围为：

- Electron 桌面端
- 单用户多设备同步优先
- 服务端为唯一真相源
- 第一阶段不做 CRDT 和实时协作

---

## 2. 设计摘要

### 2.1 最终结论

TopoMind 桌面端本地数据层建议采用三层结构：

- **结构化本地镜像层**：使用 `SQLite` 镜像核心业务实体
- **任务与状态层**：使用 `SQLite` 保存同步队列、冲突记录、游标、上传任务
- **文件缓存层**：使用本地缓存目录保存附件下载文件、缩略图、临时导出文件

### 2.2 第一阶段目标

第一阶段本地缓存层要确保五件事：

1. 常用工作区打开速度不严重依赖网络  
2. 用户写操作在弱网或短时断网时不丢失  
3. 核心实体可以稳定做本地镜像和增量更新  
4. 附件可下载到本地再走桌面能力打开  
5. 缓存损坏时可以安全重建，不影响服务端真相源  

### 2.3 第一阶段不做

- 不做完全脱网的全功能工作模式
- 不做本地缓存到服务端的双主同步
- 不做块级文档离线合并
- 不做无限保留所有历史缓存
- 不做复杂多策略冷热分层缓存引擎

---

## 3. 为什么必须有本地缓存

如果桌面端没有本地缓存，而完全依赖远端 API，会出现以下问题：

- 打开知识库和房间时明显受网络波动影响
- 图谱布局、文档和附件预览体验不稳定
- 用户短时离线后无法继续当前工作
- 同步冲突和失败无法稳定保留待处理上下文
- 桌面端“系统打开”“在文件夹中显示”等能力难以衔接

因此 TopoMind 的桌面端不应被设计成“纯在线薄客户端”。

## 4. 缓存分层

## 4.1 总体结构

推荐采用以下结构：

```text
Renderer / UI
  -> Application Services
    -> Local Repository (SQLite)
    -> File Cache Manager
    -> Sync Engine
    -> Remote Repository
```

## 4.2 三层职责

### 结构化本地镜像层

用于保存核心业务实体的最近已知状态，例如：

- `knowledge_bases`
- `cards`
- `documents`
- `graph_layouts`
- `attachments`

### 任务与状态层

用于保存同步过程中的派生状态，例如：

- `sync_outbox`
- `sync_cursor`
- `sync_conflicts`
- `attachment_upload_jobs`

### 文件缓存层

用于保存非结构化文件内容，例如：

- 附件下载文件
- 图片缩略图
- 预览转换后的临时文件
- 导出过程中的临时包

---

## 5. 为什么核心镜像用 SQLite

## 5.1 相比 localStorage

`localStorage` 只适合少量轻量状态，不适合承载：

- 结构化实体镜像
- 条件查询
- 批量 upsert
- 事务性同步应用
- 冲突和队列管理

## 5.2 相比继续使用本地工作目录 JSON

直接继续用目录文件缓存会导致：

- 结构和云端模型脱节
- 路径语义继续渗透业务层
- 增量更新、事务和索引能力不足
- 和同步协议无法自然对齐

## 5.3 SQLite 的适配点

`SQLite` 很适合承担桌面端本地镜像层，因为它具备：

- 单机嵌入式部署简单
- 事务能力成熟
- 查询能力足够强
- 可直接承接关系型实体模型
- 与 Electron 主进程结合自然

---

## 6. 哪些数据进入本地 SQLite

## 6.1 必须进入本地镜像的核心实体

第一阶段建议进入 `SQLite` 的实体如下：

- `knowledge_bases`
- `cards`
- `card_edges`
- `graph_layouts`
- `documents`
- `attachments`
- `workspace_configs`

### 原因

- 都属于高频访问实体
- 都需要和增量同步协议对齐
- 都适合通过稳定 ID 做镜像

## 6.2 必须进入本地状态层的同步对象

- `sync_outbox`
- `sync_cursor`
- `sync_conflicts`
- `attachment_upload_jobs`
- `bootstrap_jobs`

## 6.3 适合留在设备级存储、不进入云同步的内容

- 最近打开窗口列表
- 面板折叠状态
- 当前缩放偏好
- 最近使用的导出目录
- 本机附件下载目录映射
- 调试标记与开发开关

### 建议存储位置

- 少量轻配置可保留在 `localStorage`
- 稍复杂设备设置可放单独本地配置文件
- 不建议混入云同步实体表

---

## 7. 哪些数据不应该缓存或只弱缓存

以下内容不建议作为长期结构化镜像缓存：

- 鉴权 token 明文业务缓存
- 已失效的签名 URL
- 大体积附件二进制内容的无限期本地常驻副本
- 临时下载失败的半成品文件
- 仅用于一次性导出的中间文件

### 原因

- 有安全风险
- 生命周期短
- 容易导致缓存膨胀
- 和“可重建镜像”目标不一致

---

## 8. 本地表建议

## 8.1 本地镜像表

建议建立以下表：

- `local_workspaces`
- `local_knowledge_bases`
- `local_cards`
- `local_card_edges`
- `local_graph_layouts`
- `local_documents`
- `local_attachments`
- `local_workspace_configs`

## 8.2 本地状态表

- `sync_outbox`
- `sync_cursor`
- `sync_conflicts`
- `attachment_upload_jobs`
- `cache_meta`

## 8.3 本地镜像字段原则

本地镜像表字段建议分三类：

1. **远端实体字段**  
2. **本地派生状态字段**  
3. **缓存管理字段**  

### 远端实体字段示例

- `id`
- `workspace_id`
- `version`
- `updated_at`
- `deleted_at`
- `content_json`

### 本地派生状态字段示例

- `dirty`
- `has_conflict`
- `sync_status`
- `last_synced_at`

### 缓存管理字段示例

- `cached_at`
- `last_accessed_at`
- `cache_priority`

## 9. 本地镜像规则

## 9.1 只镜像“当前已知最新版本”

第一阶段本地镜像表只保存当前实体的最近已知版本，不保存完整历史版本。

### 原因

- 控制体积
- 简化读写逻辑
- 历史审计已经有服务端 `change_events`

## 9.2 本地镜像不是第二真相源

必须坚持：

- 本地镜像可脏、可旧、可重建
- 服务端提交状态才是最终权威
- 本地不能绕过同步协议直接改变云端语义

## 9.3 本地镜像更新来源

本地镜像只允许通过两种方式更新：

1. 用户本地操作写入  
2. 同步引擎应用服务端快照或事件  

### 必须避免

- UI 组件直接拼装 SQL 改镜像
- 多个子系统各自维护独立副本
- 用文件缓存内容反向推导结构化实体

---

## 10. 文件缓存目录建议

## 10.1 推荐目录结构

建议在应用缓存根目录下按用途拆分：

```text
cache/
  db/
    topomind-cache.sqlite
  attachments/
    workspace-{id}/
  thumbnails/
  temp/
  exports/
  logs/
```

## 10.2 附件缓存命名建议

附件本地缓存文件名不应只依赖原始文件名，建议包含：

- `attachmentId`
- 内容 hash 或版本信息
- 原始扩展名

例如：

```text
attachments/workspace-{workspaceId}/{attachmentId}-{sha256}.png
```

### 原因

- 避免重名覆盖
- 便于校验缓存有效性
- 便于清理和重建

## 10.3 临时文件与持久缓存分离

以下内容必须放在 `temp/`：

- 下载中的临时文件
- 预览转换产物
- 导出中的中间文件

不要和稳定缓存文件混放。

---

## 11. 离线能力边界

## 11.1 第一阶段允许的离线能力

如果本地已有缓存，第一阶段建议允许：

- 浏览已缓存的知识库和卡片树
- 查看已缓存文档
- 查看已缓存图布局
- 编辑已缓存的卡片和文档，并进入待同步队列
- 删除或恢复已缓存实体，并进入待同步队列

## 11.2 第一阶段谨慎支持的能力

- 新建 KB
- 新建卡片
- 新建文档
- 调整图布局

### 说明

这些能力理论上可以离线支持，因为 `uuid` 可预生成。  
但是否默认开放，取决于你对冲突复杂度的容忍度。

## 11.3 第一阶段不建议承诺的离线能力

- 首次未缓存工作区的完整浏览
- 附件内容的稳定离线预览
- 大规模批量导入后完全离线同步
- 多设备同时离线编辑同一文档后的无感合并

---

## 12. 离线写入策略

## 12.1 写入流程

离线或弱网时，用户写操作建议遵循统一流程：

1. 先写本地镜像  
2. 生成 `sync_outbox` 项  
3. 将实体标记为 `dirty`  
4. 如果当前离线，则等待后台恢复  
5. 网络恢复后由同步引擎统一推送  

## 12.2 本地创建实体

若允许离线创建，建议：

- 客户端本地直接生成 `uuid`
- 初始 `version` 记为本地占位版本，例如 `0` 或 `1`
- 首次成功提交后以服务端返回版本覆盖

### 推荐做法

更稳妥的做法是：

- 本地 UI 可立刻看到新实体
- 但必须显式标记 `sync_status = pending`

## 12.3 本地删除实体

离线删除不应立刻物理清除本地数据，建议：

- 标记 `pending_delete = true`
- 保留实体快照
- 待服务端确认后再切换为标准软删除状态

---

## 13. 冲突与本地保留策略

## 13.1 冲突时本地不能直接丢

检测到版本冲突后，不应立即丢弃本地修改。

### 建议行为

- 保留本地未提交快照
- 将 outbox 项标记为 `conflict`
- 将实体标记为 `has_conflict = true`
- 让 UI 层可展示“待处理冲突”

## 13.2 文档冲突保留

文档是最需要保留本地副本的实体。

### 建议保留内容

- 本地提交前的 `content_json`
- 本地标题变更
- 冲突发生时间
- 对应服务端版本号

## 13.3 布局冲突保留

图布局冲突允许策略更简单：

- 保留最近本地布局快照
- 允许用户手动选择覆盖或放弃

---

## 14. 首次启动与缓存预热

## 14.1 首次登录新设备

新设备首次登录时建议：

1. 创建本地 `SQLite` 数据库  
2. 拉取工作区 bootstrap 信息  
3. 分页同步核心实体  
4. 建立 `sync_cursor`  
5. 标记工作区为“可离线浏览”  

## 14.2 最近工作区预热

桌面端可在启动后后台预热最近访问工作区的：

- 卡片树
- 最近文档
- 当前 KB 根布局
- 小尺寸封面和缩略图

### 价值

- 打开速度更平滑
- 用户主观上更接近“本地应用”

## 14.3 不要过度预取

第一阶段不要默认预拉：

- 全量附件
- 所有历史文档
- 不活跃工作区的所有布局

否则缓存膨胀很快。

---

## 15. 缓存淘汰与清理策略

## 15.1 结构化缓存清理原则

结构化镜像原则上尽量保留，不做频繁清空。  
因为它们体积通常远小于附件文件。

### 可以清理的场景

- 用户主动退出并清除本地缓存
- 本地数据库损坏
- 工作区被移除访问权限
- 长时间未访问且明确允许释放离线数据

## 15.2 文件缓存清理原则

文件缓存必须可清理，建议优先按以下维度淘汰：

- 最近最少访问
- 文件大小
- 是否已固定保留
- 是否仍与本地存在的附件元数据关联

## 15.3 建议的缓存分类

- **Pinned**：用户显式保留离线文件
- **Warm**：近期访问过的文件
- **Cold**：长时间未访问文件
- **Temp**：临时文件，短周期清理

## 15.4 清理触发条件

- 应用启动后低优先级巡检
- 下载新文件前空间不足
- 达到自定义缓存体积上限
- 用户手动点击“清理缓存”

---

## 16. 缓存一致性与修复

## 16.1 本地数据库损坏

如果 `SQLite` 损坏，建议：

1. 备份损坏文件到 `logs/` 或 `temp/`  
2. 新建空数据库  
3. 从服务端重新 bootstrap  
4. 尝试恢复未上传 outbox 备份  

## 16.2 文件缓存丢失

文件缓存丢失不应影响结构化镜像。

### 处理方式

- 发现文件不存在时仅标记本地缓存失效
- 下次访问时重新下载
- 不修改远端附件元数据

## 16.3 游标失真

如果发现 `last_event_id` 明显异常，建议：

- 触发工作区级重新校准
- 以 bootstrap 快照重建本地镜像
- 重新记录最新游标

---

## 17. 安全与隐私考虑

## 17.1 不应明文长期保留的内容

- Access Token
- Refresh Token
- 私有下载签名 URL
- 临时鉴权头

### 建议

- 认证信息使用更安全的本地存储方案
- 到期或退出登录时主动清理

## 17.2 本地敏感附件

如果后续支持更敏感内容，建议预留：

- 文件缓存目录按工作区隔离
- 用户退出后清理策略
- 可选的本地加密能力

第一阶段可以先不强上加密，但目录隔离最好一开始就做。

---

## 18. 与当前 TopoMind 代码的衔接建议

## 18.1 现有本地工作目录不要继续充当缓存层

当前项目已有“本地工作目录即真相源”的历史模型。  
云同步重构后，建议不要让旧工作目录继续扮演新的本地缓存层。

### 原因

- 目录语义会继续绑住路径模型
- 很难和版本化实体镜像对齐
- 同步协议和本地缓存职责会混乱

## 18.2 Electron 主进程持有 SQLite 更稳

建议：

- `SQLite` 连接由 Electron 主进程管理
- Renderer 通过更薄的 service / IPC 访问
- 避免多个 renderer 自己直接持有数据库连接

## 18.3 UI 层只感知仓储状态

UI 层最好只感知：

- 当前内容
- 是否脏
- 是否离线
- 是否冲突
- 是否正在同步

不要让 UI 直接理解数据库表细节。

---

## 19. 推荐实施顺序

建议按以下顺序落地：

1. 先定义本地镜像表和状态表  
2. 先完成 `Local Repository` 的读写接口  
3. 再接入 `sync_outbox` 和 `sync_cursor`  
4. 再实现附件文件缓存管理器  
5. 最后补缓存清理、预热和损坏恢复  

### 为什么这样排

- 先把结构化镜像打稳
- 再把同步协议落地到本地
- 最后再优化体验层

---

## 20. 未决问题

正式实施前，仍需确认以下问题：

1. 第一阶段是否默认支持离线创建实体  
2. 附件文件缓存是否需要用户可配置上限  
3. 学习统计是否进入本地 SQLite，还是单独设备数据库  
4. 是否需要用户手动“固定为离线可用”的工作区或附件  
5. 本地数据库损坏后，是否尝试恢复未上传草稿  
6. 退出登录时，是删除全部缓存，还是保留非敏感离线镜像  
7. 是否要为大文档增加更细的分片缓存策略  

---

## 21. 最终建议

TopoMind 桌面端本地缓存层最关键的不是“缓存越多越快”，而是：

- 结构化镜像清晰
- 文件缓存和实体镜像分离
- 设备状态和云同步状态分离
- 本地脏数据可保留、可重试、可重建
- 一旦缓存损坏也不会伤到服务端真相源

一句话概括：

> 用 SQLite 承载结构化镜像和同步状态，用文件目录承载附件缓存和临时文件，把本地缓存设计成“可恢复的加速层”而不是第二数据源，才是 TopoMind 最稳的桌面端离线路线。

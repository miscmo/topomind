## 修复：点击编辑器后内容被描一圈蓝框（用户报"两边两个竖线"）

### 现象与根因
点击 Smart Document 正文 → 编辑区被 2px accent 蓝框圈住（用户视角：内容左右各一条竖线）。
真凶是 2026-10-31 加的全局焦点环（`src/styles/base.css`）：
- ProseMirror/BlockNote 的编辑器根 `.bn-editor` **同时带 `contenteditable="true"` 和 `tabindex="0"`**。
- `[tabindex]:not([tabindex='-1']):focus-visible` 特异性 **(0,3,0)**（`:not()` 内的选择器计入权重），
  高于我专门写的排除规则 `[contenteditable]:focus-visible` 的 **(0,2,0)**。
- 两条都是 `!important`，特异性高的胜出 → 蓝框出现。Chrome 对 contenteditable 即使鼠标点击也匹配
  `:focus-visible`，所以"点一下就冒框"。

### 修复（base.css）
- 把排除写进 tabindex 规则**自身的选择器**：`[tabindex]:not([tabindex='-1']):not([contenteditable]):focus-visible`。
- 排除规则双写 `[contenteditable]:focus-visible, [contenteditable][tabindex]:focus-visible { outline:none !important }`
  （盖住第三方库里可能存在的同类 !important 规则）。
- 教训：**想排除一类元素，别靠"后面再写一条覆盖"，要写进原规则的 `:not()`** —— 否则特异性算不过。

   reload 即自动进入工作空间。

## 节点（KnowledgeCard）设计审计 —— 为「进度/标记」需求铺路（未改代码，纯分析）

```

```
实测（v3.4）：**只有 color-mix 版生成规则**，`bg-[var(--x)]/50`、`text-[var(--x)]/60` 全部静默丢弃。
现存 4 处在 QuickNodeToolbar（分隔线不可见）+ KnowledgeCard:265（编辑态背景失效）；
同类残留还有 RightPanelContainer:102、PerformanceTab:62、TabBar:151。

### 已确认的缺陷（有行号）
1. **hover/active 边框反馈失效**：`KnowledgeCard.tsx:193` 用 class `border-[var(--color-border-strong)]`，
   但 `:198` 的 inline `style.borderColor = data.domainColor ?? nodeStyle.borderColor` 优先级更高；
   只有 selected 时才置 undefined、connectTarget 用了 `!important`。→ 默认也有 borderColor 的节点
   hover 时**完全没有边框反馈**。
2. **双轨颜色，静默覆盖**：`domainColor`（房间/域色）恒优先于用户自定义的 `nodeStyle.borderColor`
   （KnowledgeCard:198、CanvasMiniMap:233）→ 样式面板改边框色在设过域色的节点上永远不生效。
3. **emoji picker 定位一次性**：`resolvePickerPosition` 只在打开时算一次，portal 到 body；
   之后平移/缩放画布既不跟随也不关闭（KnowledgeCard:123-177）。
4. **LoD 名不副实**：`isLowDetail`（zoom<0.45）只砍了 resizer/toolbar/阴影/resizeLabel，
   标题+emoji+文档图标+徽章仍全量渲染 → 万级节点收益有限。
5. **无障碍**：徽章、emoji 都是 `div + onClick`（非 button、无 role/tabindex），键盘不可达；
   节点本身无聚焦入口。
6. **死字段**：`hasContent` 在 `graphBuilder.ts:146` 恒为 false，卡片没有正文/摘要层。
7. **职责混载**：`childCount` 徽章既显示数量又是唯一的下钻入口，childCount=0 时画布上无入口（只能右键）。
8. **扩展性瓶颈**：右槽位宽度在 `autoSize.ts:42-47` 用常量（8/16/22）手算，
   再加任何槽位（进度/标记）必须同步改常量，否则文字被遮挡；且常驻会推宽**所有**节点。

### 已修（本轮）
- **hover/active 边框反馈**：不再用 inline `border-color`；改成 inline 只写 CSS 变量 `--tm-card-border`，
  class 用 `border-[var(--tm-card-border)]` + `hover:border-[var(--color-border-strong)]` + `active:border-[var(--color-accent)]`。
  静态实测（puppeteer 加载真实 dist CSS）：旧写法 hover 后仍 `#e2e8f0`（无反馈），新写法 hover 后 `#cbd5e1` ✓。
- **双轨颜色优先级**：改为「用户显式 `data.nodeStyle.borderColor` > `data.domainColor` > 默认样式」。
  ⚠️ 不能写成 merge 后的 `nodeStyle.borderColor ?? domainColor`——`defaultNodeStyle.borderColor` 恒为 `#e2e8f0`，
  那样域色会永远失效。**必须**读未 merge 的 `data.nodeStyle?.borderColor`。MiniMap:234 同步同款逻辑。
- 分隔线 `bg-[var(--color-border-light)]`（4 处）；编辑态背景改 `color-mix` 版。

### Tailwind 新坑（补充 10-31 那条）
`border-[var(--x,var(--y))]` 这类**带逗号的 var() 回退写法同样不生成 CSS**（逗号会被当成分隔符）。
→ 需要回退值时别写进 arbitrary，改由 JS 保证变量一定有值。

### 核心设计结论（对「进度/标记」需求）
**装饰通道已占满语义通道**：背景色/边框色/emoji/徽章全部可被用户自由改写，
卡片上没有任何一条保留给「状态」的视觉通道 → 必须先**划分通道所有权**
（建议：装饰=背景/边框/字体；语义=左边缘 3px 竖条(进度)+标题前标记位），
并把语义层与 `nodeStyle` 在数据模型上分开存（`progress` / `marks` 独立字段，
不要塞进 nodeStyle，也不要复用 emoji）。
运行时字段 Selected/hovered/connectTarget/titleEditRequested 混在 `data` 里
（`graphStore.tsx:116` 有 `NODE_RUNTIME_DATA_KEYS` 兜底持久化），
加新字段时要记得这个集合；`autoSize` 的 useMemo 依赖整个 `data`，hover 也会重算 canvas 测量。

## 性能优化：缩放掉帧 + Shift 多选拖动掉帧

### 根因（两条都是「订阅粒度」问题，不是渲染引擎问题）
1. **缩放掉帧**：`KnowledgeCard.tsx` 里 `const zoom = useStore((s) => s.transform[2]); const isLowDetail = zoom < 0.45`。
   React Flow `useStore(selector, equalityFn?)` 不传 equalityFn 时按 **Object.is** 比较（已核实 `index.js:38`）。
   selector 返回**浮点** → 缩放时每帧 zoom 都不同 → **每个可见节点每帧重渲染**。
   而真正用到的只是那个布尔。
2. **多选拖动掉帧**：`useSmartGuides.ts` 两处
   - 顺序错：先 `buildNodeMeta(nodes)`（遍历整图建 4 个 `Map<number,Set<string>>`，O(N)），**然后**才判 `selectedNodeCount > 1` 返回 → 拖动起步一次大分配。
   - `setGuideLines([])` 每帧传**新数组** → React 不 bail out → 每次 mousemove 重渲染整棵画布（真正的放大器）。

### 修复（都极小，不改变可见行为）
- `KnowledgeCard.tsx`：`const isLowDetail = useStore((s) => s.transform[2] < 0.45)` —— **selector 直接返回布尔**，
  缩放期间节点侧零重渲染，只在跨 0.45 阈值时重渲染一次。
- `useSmartGuides.ts`：多选前置短路（放在 buildNodeMeta **之前**）
  `if (dragChanges.length > 1) { activeNodeMetaRef.current = null; setGuideLines(prev => prev.length===0 ? prev : EMPTY_GUIDE_LINES); return nextChanges }`
- 所有 `setGuideLines` 改**函数式更新 + 同引用 bail out**（含末尾 `guideLinesEqual(prev,new)?prev:new`），
  并抽出模块级 `EMPTY_GUIDE_LINES` 常量。
- `onNodesChangeIntercept` 用 `nodesRef` 读 nodes，deps 从 `[nodes]` → `[]`，消除每帧回调重建。
- `useGraphCanvasModel.ts`：`zoomLevel` 经 `useDeferredValue` 再喂给 CanvasMiniMap（缩略图降级为可中断）。

### 已核实的 React Flow 事实（可复用）
- `updateNodePositions` 遍历 `nodeDragItems`，为**每个**被拖节点各 push 一条独立
  `type:'position', dragging:true` change（`index.js:3403-3433`）→ **多选时 `dragChanges.length > 1` 成立**，
  这条短路判断可靠。
- `NodeResizer` 在 `isVisible=false` 时 `return null`（`index.js:4900`），**不会**留下隐藏 DOM，不是性能瓶颈。

### 通用教训（写 UI 前先想）
**订阅粒度必须贴合真实用途**：
- 要布尔就别订阅连续值（浮点/对象），否则每帧白重渲染。
- setState 传数组/对象字面量时，React **不会** bail out；想跳过重渲染必须返回**同一个引用**
  （用函数式更新 + 比较，或共享常量）。

用 esbuild 把真实 store + `buildNodeChangeOperations` 打成 CJS 在 Node 里跑（1 万节点）：

`areBusinessDataEqual` 首行就返回 true，所以并不慢。
**→ 别只盯着 store，先 bench 再动手。**

### 真正的大头在渲染层（三处）
1. **右侧面板两个 Tab 用 CSS `hidden` 常驻挂载**（`RightPanelShell.tsx`），
   隐藏的那个照样订阅、照样重渲染。框选时 `selectedNodes` 每帧都是新数组
   → `StyleSection` 每帧重建整棵 `NodeStylePanel`；其 effect 还会 `setExpandedBlocks(新对象)` 二次渲染。
2. **`DetailPanel` 订阅 `selectedNodeId`**，框选时每帧变 → 每帧重渲染整个详情面板，
   并在 effect 里为"路过"的每个节点 `loadDocuments` 读一次磁盘（只有 `isActive` 门控，管不住选中变化）。
3. **每个 selected 节点都渲染 `NodeResizer`**（8 句柄 + 4 线）：
   框选每多选中一个就挂载一整组，选中几十上百个时 DOM/reconciliation 开销可观。

### 修复（都走"降订阅粒度/降级更新"，不卸载组件）
- `RightPanelShell` 把可见性透传：`<StyleSection active={rightPanelTab==='style'} />`；

- `useKnowledgeCardModel` 新增 `isMultiSelected = useGraphStore(s => s.selectedNodeCount > 1)`

### 澄清：node data 上其实没有"运行时字段污染"（重要，别再当性能问题处理）
曾以为「hovered/connectTarget 挂在 data 上 → 悬停重建 data → 白白重跑 measureText」，
**核实后前提不成立**：
- `data.hovered`：只有读（`useKnowledgeCardModel`）、**全代码库无写入者** → 死字段，已删
- `connectTarget`：类型里定义了但**完全没人用**（高亮实际走 `graphUiStore.connectingTargetId === id`）→ 已删
- `visuallySelected`：来自 React Flow 的节点顶层 `selected` prop，不在 data 里
- `data.selected`：`grep data\.selected` 只命中 **FloatingEdge**（那是 edge 的 data，不是 node）
- 真正会写进 node.data 的运行时字段**只有 `titleEditRequested`**（创建节点后自动重命名，极低频）

结论：悬停完全走组件本地 `isHovered`，不碰 store、不重建 nodes 数组。
→ 不需要做「把运行时字段剥离出 data」的架构改动（那是过度工程）。
→ `NODE_RUNTIME_DATA_KEYS` 已精简为 `['selected', 'titleEditRequested']`
  （selected 保留是防御性的：`areBusinessDataEqual` 用它排除快照比较，移除收益为零、风险非零）。

### 实测数据（大房间，埋点 `__tmCardProf` / `__tmEdgeProf`）
缩放 2~3 秒：`卡片.render 8364 / mount 1624 / unmount 1649 / mountedNow 23`，`连线.render 3908`
Shift 框选：`卡片.render 2814 / mount 36 / unmount 45 / mountedNow 239`，`连线.render 1130`

**结论：缩放卡顿的真凶是 mount/unmount（节点进出视口），不是重渲染。**
- React Flow 的可见性判断（`index.js:2068` `getNodesInside`）用的是**精确视口矩形、无 buffer**，
  缩放时边界节点反复进出 → 实测 1600+ 次挂载，而结束时只有 23 个节点在视口里。
- 每次挂载平均伴随 ~5 次 render（8364/1624），含 React Flow 测量 dimensions 的固有更新。
- 平移不影响 zoom，所以能用"zoom 是否变化"区分缩放/平移（onMove 两者都触发）。

**对策**：`isViewportZooming`（uiStore）+ `nodes.length > 300` 时才把 detailLevel 强制降到 0 档，
让缩放期间的每次挂载只建 ~2 个 DOM 元素而非 ~12 个。翻转只在开始/结束各一次，不是每帧。
兜底：程序化变换（fitView/setViewport）可能不触发 onMoveEnd，故加了 180ms 超时自动恢复，
否则节点会永远停在最低档。

### 性能埋点读数的两个前提（别再误读数字）
- **`main.tsx:69` 开了 `StrictMode`** → DEV 下每个组件双渲染、effect 双调用，
  所以 `__tmCardProf.render` / `mount` / `unmount` **全部要除以 2** 才是真实值。
- **`FloatingEdge` 每条边渲染私有 `<defs><marker>`**（`markerUnits="userSpaceOnUse"`、
  markerId 按 edge id 唯一）→ 可见边的 SVG DOM 是 3 倍（defs + marker + path）。
  `<marker>` 是 Chromium 里最贵的东西之一，做边优化时优先从这里下手。
- React Flow 的 `NodeWrapper` 用 `shallow` 比较订阅 `{node, internals, isParent}`，
  **缩放期间这些引用不变** → 缩放不会让已挂载节点每帧重渲染，不用为它做优化。

## 修复：代码块语言下拉滚动穿透到编辑器

**现象**：代码块工具栏的语言下拉里滚轮滚到列表首尾后继续滚，整个编辑器正文跟着滚。

**根因**：`.tm-code-toolbar__menu-list`（`max-height:266px; overflow-y:auto`）是滚动容器但没有
`overscroll-behavior`，浏览器把剩余的滚动量**链式传递**给祖先滚动容器 `.tm-smart-editor-scroll`。
同类缺陷还有 `.tm-smart-block-menu`（快捷块菜单，420px + overflow-y:auto）。

**修法**：两个滚动容器各加一行 `overscroll-behavior: contain`。
（编辑器正文是原生 `overflow-y:auto` 滚动，不是 JS wheel 驱动，所以 CSS 就能拦住；
若哪天改成 JS 驱动滚动，这招会失效，需要再加 wheel 边界判断。）

**通用规则**：以后凡是「弹层/菜单/下拉内部可滚动」的容器，写 `overflow-y:auto` 时
必须同时写 `overscroll-behavior: contain`，否则滚到边界就会带着背后的内容一起滚。

**注意**：BlockNote 原生的代码块头部（含 `<select>`）已被
`SmartDocumentEditor.css:428` 用 `display:none !important` 整块隐藏，
出问题的永远是自定义工具栏 `.tm-code-toolbar`，别去给那个死 `<select>` 加样式。

## 修复：编辑行内公式时输入框自己消失 / 后续内容写错位置（偶发丢内容）

**根因链（实测确认，非猜测）**：
`blockLastModifiedExtension` 在停止输入 ~1s 后用 `setNodeMarkup` 把 `lastModified` 写回
**blockContent 节点** → ProseMirror 重建块内容节点的视图 → 行内公式的 React nodeView 被重建
→ `InlineMathRenderer` 的 `isEditing`/`draft` 全丢 → 输入框消失、焦点掉回正文，
选区还停在「点公式之前的位置」（常是块首）→ 用户继续敲字就写进错误位置，看起来像内容消失。

对照组实验：把该 extension 去掉后，编辑停顿多久输入框都在；加回来必然在 ~1s 后消失。

**修法（三处配合）**
1. `mathEditSession.ts`（新增）：`beginMathEditing/endMathEditing/isMathEditing` 计数信号。
   `blockLastModifiedExtension.flush()` 里 `isMathEditing()` 为真就推迟写入（上限 30s 兜底，防止编辑会话异常导致时间戳永不落盘）。
2. `mathSupport.tsx`：行内公式改为**本地 draft，Enter/blur/Esc 时才一次性 `updateInlineContent`**；
   编辑期间不产生 docChanged → pending 为空 → flush 根本不会来打扰。块级公式也挂上编辑信号。
3. 点击 chip 用 `onMouseDownCapture` + `preventDefault` + `stopPropagation`：
   **必须在捕获阶段拦**，冒泡阶段 React 拿到事件时 PM 已经处理完点击（改写选区→触发视图重建→编辑态立刻丢）。
   附带 `placeCursorAfterMath()`：用 `view.posAtDOM(dom,0)` 定位并把光标放到公式之后（否则提交后 `editor.focus()` 恢复旧选区）。

**顺带修的**：`SelectionMathButton` 加两道守卫 —— ① 只认 `TextSelection`（NodeSelection 范围是整个块容器，replaceWith 会把整块换成公式）；② 插入后显式把光标放到 `insertAt + 1`（`replaceWith` 只是映射原选区，映射结果仍覆盖刚插入的公式节点，继续打字会把公式替换掉）。

**通用规则**：任何「编辑器里的 React 自定义节点持有编辑态 state」都要假设**节点视图会被外部 transaction 重建**，
state 会丢。三条防线：① 编辑期间别产生文档变更；② 让会改文档的延迟任务知道「正在编辑」；③ 点击时用捕获阶段拦住 PM。
另外：不要指望 `editor.focus()` 会把光标放回「用户以为的地方」——它恢复的是停在那儿的旧选区，必要时先显式设选区。

## 修复：滚动编辑器时整个界面上移、底部露白（偶发「整页漂移」）

**现象**：编辑器正文里滚轮向下滚动，有概率整个界面（图谱 + 右栏 + 编辑器状态栏）
整体上移一段、底部露出空白，多次后内容漂出窗口，且滚不回来。

**根因（实证复现）**：目录联动（scroll-spy）对当前标题调用
`element.scrollIntoView()`（DocumentWorkspaceLayout 目录列表自动滚动）——
它会沿祖先链滚动**每一个**可滚容器。右栏外壳 / 图谱页 / 内容区都是 `overflow:hidden`，
**hidden 仍然是滚动容器**，可被程序化滚动。一旦目录项落在某外壳视口之外
（目录被拖到下方、窗口较小），该外壳就被滚动 → 整块内容上移 + 底部露白，
而 hidden 容器不接受用户滚动 → 再也滚不回来。实测单次调用即把右栏外壳滚 259px。
「偶发」= 目录项是否恰好在其外壳视口之外。

**关键事实（实验测定，别再猜）**
- **wheel 滚动链不会**带动 `overflow:hidden` 的祖先（Chrome 行为，实测即使祖先有
  滚动空间也不动）。只有**程序化滚动**会：scrollIntoView / focus / 滚动锚定。
- `overflow: clip` ≠ hidden：clip **不创建滚动容器** → 无法被滚动链、程序化滚动、
  scroll anchoring 带动。这是「只做裁剪的外壳」的正确取值。
- Tailwind v3.4 有 `overflow-clip` 工具类（已验证生成 `overflow-y: clip`）。

**修法**
1. 新增 `scrollChildIntoView(container, child)`（smartDocumentUtils）：只调目标容器
   自身 scrollTop，**绝不碰祖先链**。替换三处 scrollIntoView（目录联动、
   侧栏重命名输入框、TOC 点击兜底 → 兜底改为不动）。侧栏聚焦加 `preventScroll: true`。
2. 只做裁剪的外壳一律改 `overflow:clip`：`#root`(base.css)、App 内容区、
   `#graph-page`、`#graph-panel`、RightPanelShell。
3. 编辑器正文 `.tm-smart-editor-scroll` 加 `overscroll-behavior:contain`；
   html/body 加 `overscroll-behavior:none`。
4. `core/viewportScrollGuard.ts`（App 挂载）：根层被滚动立即复位，DEV 下打印证据
   ——既是最后一道保险，也是下次复现时的取证点。

**通用规则**：**永远不要用 `scrollIntoView`**，一律用 `scrollChildIntoView(容器, 子元素)`；
`focus()` 默认也会滚祖先，视情况加 `{ preventScroll: true }`。
新增「只裁剪」的布局外壳时写 `overflow-clip` 而不是 `overflow-hidden`。

**回归脚本联动**：`scripts/verify-critical-regressions.mts` 里有断言直指
`input?.scrollIntoView({ block: 'nearest' })`，改这类代码必须同步改断言（已改为
断言 `scrollChildIntoView(container, input)` + `preventScroll`，并反向断言禁止 scrollIntoView）。

**排查经验（Electron 无法热更新时）**：用户机器上跑的 Electron 若是生产构建
（未连 dev server，TCP 上看 renderer 与 5173 无连接），源码改动/HMR **到不了**它，
注入审计无效。且 renderer 里 `fetch`/`new Image()` 出网会走系统代理（`http_proxy`），
打本地收集端口会被拦（实测 reqfail）。想拿运行时数据，现实的通道是
`window.electronAPI.invoke('log:write'|'fs:writeAppConfig', ...)`（IPC 不走代理），
或干脆请用户在 DevTools Console 里跑脚本贴结果。

**验证手段（可复用）**：dev server（`npm run dev`，localhost:5173）能在纯浏览器里跑起来，
用 puppeteer 打开 + 临时 lab 页面（`.tmp-math-lab.html` + `src/.tmp-math-lab.tsx`，
挂载真实 `smartDocumentSchema` + 各 extension，把 editor 挂到 `window.__lab`），
就能对编辑器做程序化操作并读回文档 JSON 做断言。比 GUI 手点可靠得多，用完记得删。
lab 两个易踩点：① `BlockNoteView` 来自 **`@blocknote/mantine`**（不是 `@blocknote/react`）；
② 字典要合并 `multi_column`（见 xl-multi-column 坑），否则编辑器整体不渲染。
测侧栏块菜单：先 `mouse.move` 到块左侧槽（块 x - 20）再点

## 编辑器 DOM / 判定钩子（实测）
- heading 的 DOM：`.bn-block-content[data-content-type="heading"] > h1..h6.bn-inline-content`。
- **首个 heading 块没有 `data-level`**（只有后续经历 update 的块才由 BlockNote 补上）。
  按级别写样式请用 `> h1`…`> h6` 标签选择器，**不要**用 `[data-level="N"]`。
  副作用：现有 `[data-content-type="heading"][data-level="1"]` 那条 H1 规则
  （font-size 1.5em / padding / margin-top:0）**从未生效**，H1 走的是浏览器默认
  h1 样式。要修得改成 `> h1`，且会改变 H1 间距，属独立改动。
- **「光标在哪个块」的 CSS 钩子是 `.bn-block-outer[data-current-block="true"]`**，
  由 `currentBlockHighlightExtension` 提供（仅 editable + focused 时为 true）。
  别再自己写装饰扩展，也**别用 `:focus-within`** —— 整个编辑器是一个
  contenteditable，焦点只在编辑器根上，:focus-within 命中不了具体块。
- 想在行尾加「对操作透明」的标记（如标题的 H1~H6 水印）→ 用 `::after` 生成内容：
  不进文档 JSON、不进 textContent、不进复制选区、不参与光标定位。级别用
  `--tm-heading-badge` 变量在 `> h1`…`> h6` 上赋值，样式只写一处。

  `'before'`；首块用 before 也正常（成为新首块）。

## 标题上方留白过大（排版优化）
- 症状：每个标题上方一大片空白（H1 上方 58.8px），首块也照加，标题连标题时
  两块留白叠加（H1→H2 之间近 75px）。留白来自 heading 的 `padding-top`。
- 定为「间距表达与上一节的距离，不是标题的固定附属物」：基准收紧（正文→标题
  H1 40px → H6 18px 递减）｜首块 0｜连续标题统一 22px（与级别无关）。
- 结构：各级只设 `--tm-heading-gap-top/-bottom`，场景用 `--tm-heading-gap-*-override`
  覆盖（定义在外层 `.bn-block-outer`，标题块与侧栏共同继承）。文档顶部边距移到
  `.bn-editor` 的 `!pt-6`(24px)，不再由标题 padding 承担。
- 两个坑：① `:has()` 内不能再嵌 `:has()`（整条规则静默失效）；② **侧栏是浮层、
  不在块 DOM 子树**（实测 `matches('.smart-document-content .bn-side-menu')` 为
  false，挂在 body 下的 portal），拿不到场景变量 → 由组件按文档位置打分类标记。
- 侧栏对齐的判定要「就近选取 hit-area」（按按钮中心与标题文字中心距离），
  直接 `querySelector` 第一个会在残留浮层时选错，读数离谱（-157/-325px 那种）。

## 块侧栏（＋/⠿）按钮垂直对齐：改为运行时实测（commit 6871902）
- 症状：H2→H3 连续两行时 H3 前面的按钮明显偏下；实测按钮中心比文字中心低 9.6px。
- **根因（重要，之前判断错了）**：侧栏不仅不在 `.bn-block-outer` 子树，它根本不在
  `.smart-document-content` 里 —— BlockNote 的 `usePortalElement` 对 `null` 返回
  **document.body**（不是"原地渲染"！），而 `SideMenuController` 我们没传
  portalElement → 走默认 body。所以此前所有 `.smart-document-content .bn-side-menu…`
  规则**一条都没生效**（含按钮 26px 尺寸与 hover/active）。真正生效的是 BlockNote
  按 `[data-level]` 写死的 `.bn-side-menu` 高度 30/108/84/67px —— 那是为旧字号
  阶梯设计的；连续标题把 padding-top 从 27px 收到 9.6px 后，按钮就相对偏下。
- **教训：给浮层写 CSS 前先测 `el.closest('.smart-document-content')` / `matches()`，
  别假设它在编辑器 DOM 里。** portal 到 body 还意味着拿不到编辑器容器上的
  `--topomind-smart-body-font-size` / `--topomind-smart-heading-spacing-ratio`。
- 新方案：`SmartDocumentSideMenu` 里用 `Range.selectNodeContents(.bn-inline-content)`
  取**第一行**矩形（多行段落要贴第一行，不能用元素中心），以 SideMenuExtension 的
  `referencePos.y`（浮动层定位原点）为基准算 delta 写 inline `margin-top`；
  CSS 只留 `.tm-smart-side-menu-hit-area .bn-side-menu { height:auto !important }`。
  实测 H1~H6 × 首块/连续/正常 + 正文/引用/列表/待办/空块：Δ 全部 0 ± 0.5px。
- 两个坑：① **别用菜单自身的 `getBoundingClientRect()` 当基准** —— 刚挂载那一帧
  floating-ui 还没落位，读到 0 附近的临时值，会算出上百 px 的荒唐 marginTop；
  ② 改 marginTop 前必须 `style.marginTop = ''` 清零再量，否则逐次累加。
- 非「文字流」块（图片/文件/表格/代码块）不能用 inline content 当目标：caption 也是
  `.bn-inline-content`，会把按钮拽到图片下方。这些块回退到块顶部 30px 槽（等同原行为）。

## 目录框缩进改为相对最顶级标题（commit 后）
- 需求：目录项缩进不应死绑 H1~H6 绝对等级（旧 `paddingLeft = 10 + (level-1)*12`），
  否则全文只有 H4 时 H4 仍按固定 H4 缩进，不友好。期望相对"当前目录里最顶级标题"。
- 改法：`DocumentWorkspaceLayout.tsx` 渲染处先 `reduce` 出 `minTocLevel`，缩进改为
  `10 + (item.level - tocBaseLevel)*12`（`tocBaseLevel = minTocLevel ?? 1`）。
  只有 H4 → H4 零缩进；H2+H4 → H2 0 / H4 2 级；含 H1 时与旧行为完全一致（向后兼容）。
- 数据层 `TocItem.level` 不变（smartDocumentUtils.getSmartDocumentOutlineAndStats 仍给绝对 1~6），
  改动只在渲染层。TOC 渲染唯一入口即 `DocumentWorkspaceLayout.tsx` 的 `tocItems.map`。

## 编辑器首块 H1 顶部被裁切（根因：Tailwind 任意变体整组未生成 CSS）
- 症状：编辑器第一行是 H1 时，H1 顶部被裁、上方留白“没显示全”；H1 在段落之后则正常。
- **根因（关键，之前没料到）**：`SmartDocumentEditor.tsx` 编辑器根 className 上那一串
  `[&_.bn-container]:!pl-8 / [&_.bn-editor]:!pt-6 …` Tailwind 任意变体**整组都没生成 CSS**
  （dev 与 dist 构建里都搜不到 `.smart-document-content .bn-editor{padding-top}`，实测
  `.bn-editor` paddingTop=0、paddingLeft=54px=BlockNote 默认，证明全部失效）。
  此前把 `.bn-editor` 从 `py-4` 改成 `!pt-6 !pb-4`（标题留白优化那次）后，顶部留白实际为 0；
  叠加“首块标题 gap-top 强制 0”，首块 H1 的顶边正好贴在滚动容器上沿，被 `overflow-y-auto` 裁掉顶部。
  段落之后的 H1 靠 39.9px heading gap 兜底，所以正常——完美解释“只有首块 H1 出问题”。
- **修法**：把这组 BlockNote 盒模型重置从失效的 Tailwind class 搬到 `SmartDocumentEditor.css`
  显式写死（同文件标题间距规则用同样方式，已证实可靠生效）：`.bn-editor` 顶部 1.5rem/底部
  1rem/左右 0/min-h-0/w-full/transparent；`.bn-container` pl-8/pr-4/py-0/mx-auto/w-full/transparent。
  JSX 里那串任意变体 class 已删除。实测首块 H1 `h1Top - scrollTop = 30px`（24 编辑器留白 +
  半行距），不再裁切；容器左右 32/16px 也恢复正确。
- **教训**：这类“给 BlockNote 内部元素（.bn-editor/.bn-container）改样式”的需求，**别用 Tailwind
  任意变体**，它在本项目（tailwind 3.4.19）下整组不生成 CSS；直接写进 `SmartDocumentEditor.css`
  按 `.smart-document-content .bn-X` 作用域 + `!important` 覆盖 BlockNote 默认值最稳。
- 验证：真实组件 + puppeteer 实测两侧 padding（修复前 0/54px → 修复后 24/0），截图确认 H1 完整；
  tsc/verify:critical/graph-store/plugins:static 全通过。
